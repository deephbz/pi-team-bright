# Pi Team Bright 0.24.0-rc.4

This is a prerelease on npm `next`. It reduces how long PTB blocks the lead's
Pi main thread, and it keeps the Worker system prompt stable across model
changes. Install it by exact version:

```sh
pi install npm:@hypercarrier/pi-team-bright@0.24.0-rc.4
```

For a live Team, reload the lead's Pi first, then reload each Worker's Pi.

This release does not resolve the reported lead-pane freeze. The original live
incident is not reproduced, and startup still blocks. See "Known limits".

## Lead responsiveness

In the measured loop (10 Workers, 300 Tasks, 10,000 journal events),
`team_sync`, `alert_send`, `task_graph_apply`, `team_create` and
`ensure_worker` do not block the Pi main thread for more than 100 ms. The total
blocked time per operation stays below 300 ms. The measurement ran at load
32-90 on 10 cores. A second run at load 5-14 after the cleanup gave the same
result.

- Each coordination observation reads the Task graph once and reuses one fenced
  view. Graph recovery reuses validated revision prefixes.
- Journal reads are incremental. Cached journal events are immutable.
- Durable Task, graph and config writes use one asynchronous atomic writer.
  Each accepted write still calls fsync. Task event journal appends are
  batched.
- Locked Team config reads are asynchronous.
- Herdr, terminal and process-generation probes each have one asynchronous
  interface. The synchronous copies are gone.
- Worker placement reuses the exact Herdr layout that it already read.
- Compiled tool-result validators are cached.

## Durability and correctness

- If a journal fsync fails, PTB truncates the journal to its length before the
  append and reports the error.
- Journal reads keep the bytes of an incomplete last line, and they validate a
  cached prefix before reuse. Three old defects are fixed: a split UTF-8
  character at the read boundary, a cursor after a blank last line, and a
  malformed prefix.
- If a graph is removed while a read is in progress, the read reports that the
  graph authority needs restoration. It no longer reports a raw `ENOENT` error.

## Stable Worker system prompt

The Worker system-prompt addition no longer contains the configured model,
model-role alias, runtime model or thinking level. A change of model or
thinking level in a Session keeps the same prompt bytes. The adapter captures
the addition on the first successful Worker-profile read in a Session. Profile
edits take effect in a new or recovered Session.

## Simulator

The deterministic simulator schedules asynchronous filesystem operations. One
generation check covers sync and async filesystem effects. An actor's open
file descriptors and pending Pi input close when the actor exits. A
Node/simulator contract test checks exclusive create, file modes, short I/O,
sync and rename order, and cancellation. A replay that reaches its bound is a
typed `replay_bound_exceeded` result and counts as unsupported, never as a
pass. All 12 generated campaign samples replay. Three fixed scenarios stay
unsupported: clock gap, pane loss and cross-Session fork.

A Worker that dies before PTB admits its runtime gives `launch_stalled` with
`ask_human` after 15 s. A test now checks this behavior.

## Known limits

- Startup: PTB adds about 2.5 s of main-thread CPU on a cold jiti transform
  cache and about 0.3 s on a warm cache. Keep `TMPDIR` stable so that the
  cache stays warm. A prebuilt ESM bundle was measured and deferred.
- Worker pane start still shows startup gaps of 100-1200 ms. Most of this time
  is the Pi loader. One PTB gap remains: the lock owner file uses a synchronous
  write (one sample of 102 ms).
- Long operations show no progress and cannot be cancelled.
- Key echo and Escape under load were not measured.
- A reader in the same process can see a journal event before its fsync
  completes. Receipts still wait for fsync. PTB adds no reader fence in this
  release.
- `npm run probe:model-tools` still fails with `ERR_PACKAGE_PATH_NOT_EXPORTED`
  under the ts-node loader. The failure predates this release.
