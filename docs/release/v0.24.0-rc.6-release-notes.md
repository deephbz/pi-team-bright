# Pi Team Bright 0.24.0-rc.6

This is a prerelease on npm `next`. It fixes the lead-pane freeze in
long-lived lead Sessions, and it hardens Worker Membership. 0.24.0-rc.5 was
not published, so this release contains its changes too. Tasks, Alerts and
the on-disk formats do not change.

## Upgrade from 0.24.0-rc.4

1. Install the exact version. `/reload` alone keeps the pinned old version.

   ```sh
   pi install npm:@hypercarrier/pi-team-bright@0.24.0-rc.6
   ```

2. Reload the lead's Pi first, then reload each Worker's Pi.

No data migration is necessary. Existing Teams, Members, Tasks and journals
stay valid. After the reload, `worker_stop` can stop a Worker that rc.4 left
in a stuck launch state; then call `ensure_worker` again.

## Lead-pane freeze

Four loops on the lead's Pi main thread were quadratic in the lead Session
length. They run at every `team_sync` and every sync-liveness probe. Each loop
now makes one pass:

- `team_sync` rebuilt the branch ID list once for each held entry.
- The branch context update searched the branch once for each ID.
- The baseline selection tested each entry against the full ID list.
- The branch observation copied the branch prefix at every Team update.

A regression test drives the observation service with 30,000 Session entries
and 1,500 Team updates. Those operations took 18.3 s before the fix and take
about 30-60 ms after it. Results do not change.

## Worker Membership

One total state machine in `src/team-authority/membership-machine.ts` is now
the only writer of Member lifecycle fields. It parses every persisted Member
shape. It applies, keeps or refuses each lifecycle event with a named reason.
The direct field writers and generic lifecycle patches are gone. The project
report is `docs/projects/state-machines/report.md`.

Visible behavior changes:

- **Spawn refusal:** a spawn that fails before it reaches the terminal (for
  example, no room for a pane) reports a refusal with its cause. It no longer
  reports `created`, and it adds no Member.
- **Terminal refusal:** a launch that the terminal refuses records `refused`
  with the terminal's fact. Later spawns no longer blame another Worker's
  leftover record.
- **Stop:** `worker_stop` on a leftover launch record (`requested`, `unknown`
  or `refused`) succeeds when no process can exist, with no terminal kill. A
  stop without proof of `process_stopped`, `no_process_possible` or
  `session_left` is refused as `process_may_exist`.
- **Retry:** an expired Herdr launch that never started retries automatically
  (`first_binding_retry`) on the next `ensure_worker`. A launch that can still
  bind gives `attention` with `launch_pending` and `wait`. The skill documents
  both.

Evidence:

- The simulator replays the live wedge of 2026-10-16. rc.4 leaves 3 records
  that no tool can stop. This release reports both refusals with their pane
  geometry cause and leaves no records.
- The seven live wedge records replay to 1 recovered launch and 6 stops, with
  0 terminal kills.
- The exhaustive explorer covers 3,154 states. Two-stage states that only a
  human can clear drop from 45 to 1. The remaining state is a pre-rc.1 record
  without a launch fence, and the machine refuses its stop.
- 44 simulator runs (202 Membership changes) conform to the machine with 0
  violations.

## Known limits

- No test covers a Team with mixed versions. Reload the lead first to keep
  that period short.
- If a Herdr split succeeds but the target write then fails, the pane has no
  Membership record.
- Attention reasons are still free strings. The pane-placement refusal does
  not name an operator action.
- The machine trusts the shell's `refused` and stop-authority evidence.
- No tool repairs an `invalid` Membership record.
- The fast `npm test` lane takes about 10 s longer, because of the added
  simulator wedge replay.
- Startup limits from 0.24.0-rc.4 remain.
