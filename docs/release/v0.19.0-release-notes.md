# Pi Team Bright v0.19.0

This release adds named model roles, automatic Team update delivery, a Task
Attempt timeline, and `/ptb doctor`. It also hardens graph recovery, replay,
Membership fencing, and Task delivery.

## Named model roles: breaking change

New Workers select a role from `pi_team_bright.model_roles`. Each role defines a
qualified `provider/model-id`, thinking level, and usage guidance. Set
`default_model_role` when Worker creation may omit a role. Otherwise pass
`model_role` to `ensure_worker`. An invalid or absent selection refuses before
Worker creation. Existing Workers keep their creation binding. A human model
change in Pi still controls the current Session.

Before changing settings, finish or stop live Teams on their original version.
Preserve their Team stores and Pi Session logs. Then upgrade from `0.18.0`:

1. Rename `model_profiles` to `model_roles`.
2. In each entry, join the old `provider` and `model` values with `/` and store
   the result as `model`. Keep `thinking` and `use`.
3. Set `default_model_role` to the intended role name. Remove
   `worker.default_model`.
4. Change saved `ensure_worker` calls from `model` to `model_role`.
5. Install `0.19.0` and restart Pi. Resolve any settings warning. Start new
   Team epochs before creating Workers.

A legacy Team with a raw model default cannot create new Workers under this
contract. Its existing Worker binding and Session evidence remain readable. See the
[settings example](https://github.com/deephbz/pi-team-bright/blob/v0.19.0/docs/examples/pi-team-bright.settings.json) and
[upgrade guide](https://github.com/deephbz/pi-team-bright/blob/v0.19.0/README.md#upgrade-from-model-profiles).

## Team updates and Task view

The framework can resume the leader when Team updates arrive after a reply. It
batches changes by count or delay. `/teamsync` requests one immediate check; an
empty check shows a notice and starts no model turn. An idle Team can still have
unfinished Tasks. The [synchronization record](https://github.com/deephbz/pi-team-bright/blob/v0.19.0/docs/projects/team-sync-continuity.md)
defines the observed behavior and limits.

`/pi-team-graph` opens in DAG view. Press `v` to show a timeline of recorded
Task Attempts in the same pane. Each retry has its own row. Missing historical
timing stays unavailable. The bars show elapsed time, not model effort. See the
[timeline guide](https://github.com/deephbz/pi-team-bright/blob/v0.19.0/README.md#mission-graph-semantics).

## On-demand doctor and recovery

`/ptb doctor` sends a packaged repair guide and sampled local Team metadata to
the agent in a visible turn. Use `/ptb doctor <team-name>` to inspect a named
Team. The command does not change Team authority. Its sample is not a health
guarantee; refresh authority before mutation. Other PTB commands keep their
names. See the [doctor guide](https://github.com/deephbz/pi-team-bright/blob/v0.19.0/skills/pi-team-bright/references/team-doctor.md).

Graph reads now reject selected corrupt snapshots and inconsistent replay
receipts. Runtime writes recheck the current Membership and process generation.
Task event recovery and delivery reject stale graph work. Bounded formal models
and adversarial tests cover these selected invariants; they do not prove all
runtime behavior. The [hardening record](https://github.com/deephbz/pi-team-bright/blob/v0.19.0/docs/projects/formal-hardening.md) states
the evidence and remaining limits.

Install after publication with
`pi install npm:@hypercarrier/pi-team-bright@0.19.0`, then restart Pi. Pi
`>=0.83.0` remains required. The read-only Membership observation protocol
remains `pi-teams-observation/1`.
