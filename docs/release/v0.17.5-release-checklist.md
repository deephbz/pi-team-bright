## Compatibility and boundaries

Version `0.17.5` changes packaged agent operating guidance only. It changes no
Team storage schema, Task graph, model-tool, Membership, runtime, terminal, or
Worker protocol contract. The sync ordering is guidance; it does not claim
runtime enforcement or permanent subscription behavior.

- Team identity follows a project or durable coordination boundary.
- Worker identity follows coherent semantic scope or deliberate perspective
  isolation.
- Task identity follows one bounded outcome.
- The project lead preserves user intent, constraints, approach, decomposition,
  outcomes, and trade-offs; delegation does not transfer accountability.
- The coordinator assigns Tasks, supplies context, resolves blockers, supervises
  outcomes, and escalates decisions to the user.
- A new request, terminal Task graph, empty ready front, or idle interval does
  not prove Team completion.
- A new Worker must unlock parallelism, establish reusable scope, or isolate
  perspective.
- Dependent implementation, execution, diagnosis, and repair normally preserve
  one Worker's causal context.
- Independent review and alternative experiments may use fresh Workers.
- Task graph assignment and goal or dependency changes stay separate from Alerts
  and context updates.
- While assigned nonterminal Tasks remain, interim user replies, progress notes,
  and blocker escalations end with `team_sync({view:"updates"})`, unless the
  owner explicitly pauses or stops the work. Avoid identical empty sync loops by
  naming the blocker and next actor.
- `team_sync` is a bounded observation and wait call. `caught_up` and
  `indeterminate` can return while Tasks remain nonterminal.
- Do not copy private machine paths or live Team payloads into tracked content.
