# Pi Team Bright v0.17.5

Status: stable patch candidate. This document becomes the GitHub Release body
after source, hosted, registry, and provenance gates pass.

## Lead the project and coordinate execution

The packaged operating skill gives the one lead two responsibilities. As project
lead, the lead communicates with the user, preserves intent and constraints,
chooses an approach, decomposes work, evaluates outcomes, and explains
trade-offs. As coordinator, the lead assigns Tasks to suitable Workers, provides
context and resources, resolves blockers, supervises outcomes, and escalates
decisions to the user. Delegation does not transfer accountability or the user's
authority.

Task graph assignment remains separate from Alerts and context updates. Alerts
carry exceptional clarification or attention, while goals, assignments, and
dependencies belong in the Task graph. Context records execution meaning; it does
not revise an accepted Task definition.

## Supervise in-flight work

Assigned nonterminal Tasks include waiting and blocked Tasks. While any remain
and the owner has not explicitly paused or stopped work, each user-facing reply
or progress note is an interim message. The lead makes
`team_sync({view:"updates"})` the last action before yielding. This also applies
to blocker escalations. A mutation receipt does not replace this sync: it reports
the lead's write, while sync observes other Workers and waits for later changes.

The guidance preserves explicit owner pause and stop instructions. It also avoids
identical empty sync loops: when no actor can progress, the lead states the
blocker and next actor. `team_sync` remains a bounded observation and wait call;
this release makes no runtime enforcement or permanent-subscription claim.

## Keep Team topology aligned with durable work

The packaged operating skill separates the lifecycles of Team, Worker, and Task.
A Team follows one project or durable coordination boundary and remains alive
across related requests, terminal Task graphs, empty ready fronts, and idle
intervals. Only an explicit owner or operator decision ends or resets that
boundary.

Worker creation now has a positive criterion. Add a Worker when it unlocks parallel
independent work, establishes a distinct reusable semantic scope, or deliberately
isolates context or perspective. Otherwise reuse suitable current capacity.
Implementation, execution, diagnosis, and repair normally preserve one Worker's
causal context; independent review and alternative experiments can use fresh
Workers when independence itself is valuable.

This keeps Task granularity separate from Team topology. A new Task no longer
implies a new Worker, and completed Tasks do not imply Team shutdown.

## Compatibility

Version `0.17.5` changes packaged agent operating guidance only. It changes no
Team storage schema, Task graph, model-tool, Membership, runtime, terminal, or
Worker protocol contract. Existing Teams remain compatible and should not be
recreated for this update.

## Install

Install the exact version and restart the Pi processes that must load the
updated packaged skill:

```sh
pi install npm:@hypercarrier/pi-team-bright@0.17.5
```
