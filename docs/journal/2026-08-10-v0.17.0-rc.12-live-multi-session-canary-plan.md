# rc.12 live multi-Session canary plan

Date: 2026-08-10
Stage: hardening
Status: completed for the pre-rebase source; the audit-branch rebase requires a fresh run

## Purpose

Prove the live DAG path with one fresh Pi coordinator and two fresh Worker
Sessions. This is the release guard in the rc.12 plan. It proves real carrier
startup, exact Session binding, Worker-authored Task events, and mechanical
successor delivery. It does not replace aggregate, package, or privacy gates.

The source contract remains in `extensions/index.ts`,
`src/adapters/durable-task-orchestration.ts`, and
`src/task-authority/ready-dispatch.ts`. This plan is the one-run procedure and
result-record layout.

## Preconditions

1. Stabilize the source tree. Do not run the broad aggregate lane again here.
2. Confirm the new startup reconciliation call has focused test evidence.
3. Remove only the disposable `ptb-rc12-canary-4` tmux session. Do not alter
   unrelated terminal sessions or historical Team records.
4. Load `pi-teams-proxy` from the shared skill catalog. Start the coordinator
   with `_codex_with_proxy` and `openai-codex/gpt-5.6-terra:medium`.
5. In the coordinator child, record that `HTTPS_PROXY`, `ALL_PROXY`, and
   `NO_PROXY` are present. Do not record proxy values.
6. Use a new isolated `PI_CODING_AGENT_DIR` that links only the required auth
   material. This prevents discovery of a second Pi Team Bright extension.
7. Use a new Team name, a new Beads workspace, and new operation IDs. Keep raw
   Session, tool, and terminal records outside the repository.

If proxy inheritance, exact extension selection, or one Worker startup fails,
stop the canary. Save redacted failure facts in the result artifact. Do not use
`agentLoopReady`, runtime polling, or a manual Session-binding fallback.

## Procedure

1. Start the isolated coordinator in a fresh tmux session. Verify it loads this
   working-tree extension once.
2. Create the fresh Team. Ensure two Workers: `maker` and `reviewer`.
3. Create one atomic graph with three assigned Tasks and these edges:
   `plan` (`maker`) -> `implement` (`maker`) -> `review` (`reviewer`).
   Give each Task a unique request key and a clear verification signal.
4. Wait through `team_sync({view:"updates"})`. Treat its durable Task event as
   the progress signal. A Worker-authored Task event is the launch signal.
5. Have `maker` claim and close `plan` with a result journal entry. Record the
   exact Task version and event reference. Do not make a leader Task mutation.
6. Prove that `implement` reaches `maker` through ready-front delivery. Have
   `maker` claim and close it with a result journal entry.
7. Prove that `review` reaches `reviewer` through ready-front delivery. Have
   `reviewer` claim and close it with a result journal entry.
8. For every Worker update, verify the exact Task ID, opaque version reference,
   actor Session, and Worker identity agree with the Team state. Record only
   redacted identifiers in tracked evidence.
9. Reconcile with `team_sync({view:"updates"})` until it reports the completed
   graph. Stop both Workers after their assigned Tasks are terminal. Reconcile
   once more, then shut down the Team.

## Pass conditions

The canary passes only when all conditions hold:

- The coordinator used the required proxy wrapper and Terra medium model.
- The coordinator loaded the intended source once, and both Worker Sessions
  bound to the fresh Team.
- The graph was one atomic creation with no separately linked Tasks.
- `plan`, `implement`, and `review` each have a Worker-authored Task event.
- `implement` followed `plan`, and `review` followed `implement`, without a
  leader Task update or manual dispatch.
- Each claim used the current opaque Task version. Each closed update has a
  Worker result journal entry.
- The final observation shows every Task closed. Both Workers stop before Team
  shutdown.

A failed or incomplete condition is a failed canary. It is not evidence of
release readiness.

## Result artifact

Write one redacted JSON artifact under `docs/journal/artifacts/` and one short
journal receipt after the run. Include the source commit, package version, Pi
version, model name, terminal adapter, fresh Team name redaction, source digest
set, operation-ID redactions, and timestamps. Include event-order evidence for
Team creation, Worker Session binding, graph creation, the three Worker Task
updates, successor delivery, stops, and shutdown.

State the exact pass or failure condition. State that raw Session, provider,
terminal, proxy, and authority records remain outside Git. State the next
release gate. A passing canary delivers the aggregate, package, and privacy
successor gates. It does not authorize a push, tag, npm publication, registry
change, or GitHub release.
